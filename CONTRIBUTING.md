# Contributing to Brok-AI

Thank you for considering contributing to Brok-AI. We welcome developers, testers, designers, technical writers, translators, and people who want to improve practical open-source AI software.

These are organization-wide guidelines. Individual repositories may define additional requirements; when they do, follow the repository-specific instructions.

## 1. Before You Start

- Read the repository README and documentation.
- Check existing issues, discussions, and pull requests.
- Confirm that your proposed change fits the project's scope.
- Review the repository license and any project-specific contribution rules.
- For substantial changes, open an issue or discussion before investing significant work.

## 2. Ways to Contribute

You can help with:

- Bug fixes and reliability improvements
- Features and user-experience improvements
- Tests, debugging, and compatibility checks
- Documentation, examples, and tutorials
- Translations and localization
- Performance, accessibility, and maintainability
- Responsible security improvements

## 3. Reporting Bugs

Use the repository's bug report template when available. A useful report includes:

- A concise and descriptive title
- The affected project version or commit
- Operating system, hardware, and relevant runtime versions
- Clear steps to reproduce the issue
- Expected behavior and actual behavior
- Relevant logs, screenshots, or error messages

Remove passwords, access tokens, API keys, personal data, and other secrets before sharing logs.

## 4. Suggesting Features

A feature proposal should explain:

- The problem or use case
- Why the change would be useful
- A proposed behavior or implementation
- Alternatives and possible trade-offs
- Compatibility or performance considerations, where relevant

Use the feature request template when one is available.

## 5. Development Workflow

A typical contribution workflow is:

1. Fork the relevant repository, if appropriate.
2. Create a focused branch.
3. Follow the project's architecture and coding conventions.
4. Keep commits small and descriptive.
5. Add or update tests when practical.
6. Run the relevant tests and checks.
7. Update documentation when behavior changes.
8. Open a pull request describing the change and its verification.

Suggested branch names:

- `feature/short-description`
- `fix/short-description`
- `docs/short-description`
- `refactor/short-description`

## 6. Pull Requests

A good pull request should:

- Have a clear title and explain the motivation.
- Describe the implementation and user-visible impact.
- Link related issues when applicable.
- Include test results and relevant environment details.
- Avoid unrelated changes.
- Include screenshots or logs for UI or behavior changes when useful.
- Mention known limitations or follow-up work.

Maintainers may ask for revisions or decline changes that do not fit the project's goals, quality standards, or maintenance capacity.

## 7. Code Quality and Testing

Contributors should aim for readable, maintainable, and appropriately tested code.

- Follow existing formatting and style conventions.
- Avoid unnecessary dependencies.
- Consider supported operating systems and runtime versions.
- Handle errors safely and avoid exposing secrets.
- Add tests for new behavior where practical.
- Do not claim tests passed unless they were actually run.

AI-related contributions should also consider privacy, user control, reliability, transparent behavior, and safe handling of prompts and generated content.

## 8. Commit Messages

Use concise, descriptive commit messages. Suggested prefixes:

- `feat:` new functionality
- `fix:` bug fixes
- `docs:` documentation
- `test:` tests
- `refactor:` code restructuring
- `build:` build or dependency changes
- `ci:` continuous integration
- `security:` security improvements

Example: `fix: handle unavailable local model`

These conventions are recommendations unless a repository specifies stricter rules.

## 9. Security

Do not disclose exploitable vulnerabilities in public issues or pull requests. Follow the private reporting guidance in the relevant repository's `SECURITY.md`.

## 10. Community Expectations

All contributors are expected to follow the Brok-AI [Code of Conduct](CODE_OF_CONDUCT.md). Be respectful, assume good intent, and keep feedback constructive.

## 11. Project-Specific Requirements

Individual projects may define additional rules for supported platforms, dependencies, tests, release procedures, coding standards, and contribution licensing. Those instructions take precedence over these general guidelines when they are more specific.
